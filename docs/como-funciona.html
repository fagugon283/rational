rational-agnostic: qué se hizo, por qué y cómo funciona

1 · El problema y el hueco en el mercado

Cuando varios agentes de IA —de distintas compañías— trabajan sobre un mismo código, se pierde el porqué: por qué existe una función, qué se decidió y qué se descartó, qué aprendió el equipo. El contexto se evapora entre sesiones y entre agentes, y se malgastan tokens recargando historia.

La competencia cubre piezas sueltas, pero ninguna resuelve el conjunto de forma neutral:

HerramientaQué aportaLimitación
AGENTS.mdEstándar abierto (Agentic AI Foundation) leído por 20–25 herramientasMarkdown libre sin esquema; describe build/convenciones, no gobernanza
Letta / Mem0Memoria compartida entre agentesAtadas a su propio framework; no agnósticas de editor
ADRRegistros de decisión referenciados por ID en el códigoNadie hace bien la búsqueda por hash de función → decisión
LangGraph / CrewAI / MastraOrquestación y estadoLigadas a su runtime

El hueco: un registro neutral, portable y en ficheros —decisiones, trazabilidad, memoria, tareas y aprendizaje— que cualquier agente de cualquier fabricante alimenta y consulta, por encima de todos los frameworks.

2 · Qué se construyó

Un paquete npm con tres interfaces sobre un único núcleo:

  • Servidor MCP (22 herramientas) — lo que hablan los agentes modernos.
  • CLI (rational-agnostic / ragn) — para humanos, hooks de git y CI.
  • Librería TypeScript — para integraciones a medida.

3 · Estructura de ficheros

Todo vive en ficheros dentro del repo (diffables en git). AGENTS.md es un manifiesto genérico: explica cómo se usa el sistema, nunca de qué va tu proyecto.

# manifiesto genérico: cómo usar + dónde está todo (sin el dominio del proyecto)
AGENTS.md
.rational-agnostic/
  config.json          # locale, canonical:"en", embeddings, reglas
  decisions/  D-*.md    # 1 decisión = 1 fichero (Context/Decision/Why/Consequences)
  tasks/      T-*.md     # 1 tarea = 1 fichero
              board.json # índice de estados
  memory/     shared.md  # memoria compartida entre agentes
              agents/*.md
  knowledge/  learnings.md  conventions.md
  index/      registry.json # función (file+symbol) → decisión + SHA-256
              embeddings/   # índice semántico (caché, gitignored)
              locks/

Canónico en inglés: tu locale puede ser es, pero decisiones, memoria, tareas y learnings se escriben siempre en inglés, para que sean portables y buscables por cualquier agente.

4 · Decisiones: el porqué, por escrito

Cada elección no trivial se registra como un fichero estilo ADR con secciones fijas. El sistema devuelve un ID (p.ej. D-7f3a2c) que se incrusta en el código.

// @why: D-7f3a2c
export function issueToken(user) { /* ... */ }

El comentario es estable: sobrevive a reediciones y lo entiende cualquier agente. Los IDs de decisión son hex aleatorio de 6 (sin contador central → sin colisiones entre agentes en paralelo); tareas y learnings usan IDs secuenciales bajo bloqueo.

5 · Trazabilidad por hash (coge una función, encuentra su porqué)

Al etiquetar una función, el sistema guarda en registry.json un SHA-256 del cuerpo (normalizado: insensible a reindentación, sensible a cambios reales). Eso habilita la búsqueda inversa por ubicación o por hash, y detección de deriva.

rational-agnostic why src/core/lock.ts withLock      # función → porqué
rational-agnostic why --hash <sha256>                # hash → porqué

6 · Contexto con presupuesto de tokens

En vez de volcar todo el historial, get_context arma un paquete mínimo relevante: la tarea activa, las decisiones y learnings más afines (ranking semántico) y una cola de memoria compartida, recortado a un presupuesto de tokens.

rational-agnostic context --task T-0001 --budget 1500

La búsqueda semántica usa embeddings locales por defecto (all-MiniLM-L6-v2, sin API key, offline); si la dependencia opcional no está, hay un fallback léxico determinista para que la búsqueda funcione siempre. El índice vectorial es una caché reconstruible (reindex); los ficheros markdown son la fuente de verdad.

7 · Memoria compartida y estado de tareas

Memoria

memory/shared.md es el punto de encuentro multi-vendor: un agente de OpenAI lee lo que dejó uno de Anthropic. Entradas atribuidas y con fecha vía append_memory.

Tareas

Una tarea por fichero + un board.json que da el estado de todas de un vistazo (backlog → todo → doing → review → blocked → done) sin leer cada fichero.

8 · Aprendizaje (el sistema mejora)

Capa de conocimiento híbrida: los agentes registran learnings explícitos cuando detectan algo reutilizable (record_learning), y un distill determinista mina las decisiones en busca de patrones recurrentes y reversiones. Así, antes de decidir, un agente consulta lo aprendido y no repite errores ya razonados.

9 · Adopción en un proyecto ya hecho (brownfield)

Punto clave: la herramienta no entiende tu código por sí sola —eso lo hace el LLM. El reparto:

  • La herramienta (determinista): adopt inventaría el repo (lenguajes, manifiestos, puntos de entrada, ficheros grandes, cobertura de tags) y genera un plan + prompt de onboarding.
  • El agente que elijas: lee el inventario y AGENTS.md, explora y hace record_decision + tag_code de forma incremental.

Integridad: el agente tiene prohibido inventar porqués. Si no puede inferir algo, lo anota como pregunta en memoria compartida y te consulta. init es no destructivo y verify no falla por código legacy sin etiquetar.

rational-agnostic adopt            # inventario + plan (dry-run)
rational-agnostic adopt --write    # baseline + tarea + brief en memoria

10 · verify: los dientes en CI y pre-commit

Comprobaciones deterministas cuya severidad decides en config.json: tags huérfanos (apuntan a una decisión inexistente), anclas a ficheros desaparecidos, tareas con estado inválido, decisiones con "Why" vacío. Sale con código ≠ 0 ante errores, así que encaja en un hook o pipeline. Un .rationalignore excluye fixtures y ejemplos.

rational-agnostic verify   # OK — 0 error(s) / exit 1 si falla

11 · Por qué se diseñó así

DecisiónPor qué
Capa por encima de los frameworks, no un frameworkEl hueco es un registro neutral y portable; mantenerlo determinista preserva la integridad
Tag @why estable + hash en registroEl tag sobrevive a ediciones; el SHA habilita búsqueda inversa y detección de deriva
Ficheros + locking (sin servidor)Portable en git, y agentes de distintos fabricantes colaboran sin infra
Embeddings locales por defectoOffline, gratis y privado; fiel al nombre "agnostic"; proveedor enchufable
Persistencia en inglésBase de conocimiento buscable y portable entre agentes y en el tiempo
AGENTS.md genéricoPortable y sin filtrar el dominio del proyecto; el porqué vive en las decisiones
Aplazar daemon central y autotraducciónMenos complejidad; el agente escribe inglés mejor que un traductor empotrado

12 · Cómo usarlo

Instalar y arrancar

npm install -g rational-agnostic        # o: npx rational-agnostic <cmd>
cd tu-proyecto
rational-agnostic init                   # crea AGENTS.md + .rational-agnostic/
rational-agnostic adopt                  # si ya tiene código: inventario + plan

Conectar un agente por MCP

{
  "mcpServers": {
    "rational-agnostic": { "command": "npx", "args": ["rational-agnostic", "mcp"] }
  }
}

El protocolo del agente

  1. get_context primero (ahorra tokens).
  2. Ten una tarea; mantén su estado con set_task_status.
  3. Antes de codear: record_decision → te da un D-xxxx.
  4. Etiqueta el código con // @why: D-xxxx y tag_code.
  5. Comparte con append_memory; destila con record_learning.
  6. verify debe pasar.
